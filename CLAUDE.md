## Стан проєкту

- Етап: **вибір теми** (перший із трьох етапів навчального проєкту: вибір теми → альфа-версія → остаточна версія). Проєкт реєструється у викладача разом із показом лаби 1; код альфа-версії вже пишеться.
- Структура репозиторію зафіксована в ADR-0001. CI (GitHub Actions) збирає й тестує кожен PR.
- **ЦА:** доменна модель, EF Core + SQLite, gRPC-шлюз агентів і бота (прив'язка Discord-акаунта за кодом, середовища, контейнери, start/stop/restart), команди контейнерів з авторизацією (`AuthorizedCommand`), `ICurrentUser` і фільтрація за видимістю, `/api/me`, вхід за паролем (ASP.NET Identity, cookie `cf_session`, `/api/auth/*`, перший адміністратор із `CF_BOOTSTRAP__*`), керування користувачами й ролями `/api/users/*`, пайплайн деплою з публічного git-репозиторію (без SOPS) з логом та історією деплоїв, restart і down розгорнутого стеку (`StackCommandService`); креди registry на середовищі, зашифровані Data Protection (ADR-0003). API панелі для середовищ і контейнерів (`/api/environments/*`); решта — тимчасові `/api/dev/*` і dev-автентифікація `X-Dev-User` поруч із cookie.
- **Агент:** реєстрація, з'єднання з heartbeat і перепідключенням, `ListContainers` і start/stop/restart через Docker.DotNet.Enhanced, обробники `DeployStack`, `RestartStack`, `DownStack` через `docker compose` (креди registry — тимчасовий `DOCKER_CONFIG`), Docker-образ із docker CLI і compose-плагіном, скасування команд за `CancelRequest` (ЦА надсилає його, коли перестає чекати результат). Файли стеку пишуться на місці за маніфестом (ADR-0004); деплой перевірено вживу на `example-voting-app`.
- **Ще немає:** форми видачі ролі в панелі (зона Денисенко Л. В.; чекає API зі списком середовищ і стеків), журналу аудиту, 2FA і зовнішніх входів, приватних репозиторіїв (токени), SOPS, webhook-деплою, SignalR і live-оновлень, стрімінгу логів, решти екранів панелі (є вхід, користувачі, власний обліковий запис, прив'язка Discord і контейнери), API й екранів каналів і правил сповіщень, сповіщень про контейнери й агентів.
- **Бот:** клієнт ЦА по gRPC (`IForestClient` → `GrpcForestClient`); slash-команди `/environments`, `/containers`, `/start`, `/stop`, `/restart`, `/stacks`, `/stack-restart`, `/stack-down`, `/link` на Discord.Net з автодоповненням; усі відповіді ephemeral; Docker-образ (`src/DiscordBot/Dockerfile`) і приклад розгортання `deploy/discord-bot/compose.yaml`; сповіщення про результати деплоїв у Discord-каналах (потік `WatchNotifications`).
- Дедлайни лабораторних: лаба 1 — 02.10.2026 (перенесено з 25.09), лаба 2 — 23.10.2026, лаба 3 — 13.11.2026. Дедлайни етапів проєкту ще не відомі.
- Ролі затверджено (`docs/project-overview.md`, «Команда»). Роль не обмежує, де учасник пише код: елемент лаби зараховується тому, хто його реалізував.

## Правила роботи для Claude Code

- `README.md` — публічна сторінка проєкту для відвідувачів репозиторію; технічні деталі й правила команди туди не додавати, а посилатися на `docs/architecture.md` і `CONTRIBUTING.md`.
- Спілкування й документація — українською. Ідентифікатори, коментарі в коді, повідомлення комітів — англійською.
- Відповідати прямо, на рівні реалізації, з робочим кодом, а не концептуальними оглядами.
- **Інваріанти безпеки з `docs/architecture.md` не порушувати.** Якщо задача вимагає їх порушити, зупинитися й спитати.
- Контракти `.proto` змінювати лише сумісно: нові поля й нові варіанти `oneof`, без перенумерації чи видалення (видалене поле — у `reserved`). Версії в пакеті немає (ADR-0002), тому несумісна зміна означає одночасне оновлення ЦА й усіх агентів — її уникати. Виняток: контракт вважається чернеткою (можна змінювати несумісно), доки в `main` не змерджено перший код ЦА, агента чи бота, що його використовує.
- Кожен клас, метод і екран зараховується конкретному учаснику (див. «Вимоги курсу»). Якщо незрозуміло, чия це частина коду, спитати. Після додавання елементів нагадати оновити `CONTRIBUTIONS.md`.
- Нову залежність не додавати мовчки: назвати її, пояснити навіщо, і якщо вона може піти в ретроспективу лаби 3, сказати про це.
- Коміти за Conventional Commits (`feat(agent): ...`), жодних прямих комітів у `main`. PR інших учасників мерджаться лише з аппрувом Петренка Б. О. (`.github/CODEOWNERS` додає його рев'юером); перед мерджем перевіряти, що база PR — `main`, а не гілка іншого PR.
- Архітектурне рішення, яке змінює щось із розділу «Рішення», оформлювати як ADR у `docs/adr/`.

## Рішення та їх обґрунтування

| Рішення | Чому |
|---|---|
| Шари ЦА `Domain ← Application ← Infrastructure ← Api`, без SharedKernel; `src/Contracts` — лише `.proto`-файли, код генерує кожен споживач (ADR-0002); веб отримує типи з OpenAPI-документа, який комітиться (ADR-0001, ADR-0002) | Спільний між застосунками лише протокол; зміни HTTP-контракту видно в диффі PR |
| Агент на кожному хості сам відкриває gRPC bidi-стрім до ЦА | На хостах немає вхідних портів, Docker API не виставляється в мережу, працює за NAT |
| gRPC, а не SignalR, для агентів і бота | Жорсткий контракт у `.proto`, природний стрімінг логів, агент теоретично можна переписати іншою мовою |
| Request/response поверх стріму через `request_id` + `TaskCompletionSource` | gRPC-стрім не має семантики запит→відповідь |
| SOPS розшифровується лише в ЦА; окрема age-пара на кожне середовище | ЦА і так має root-еквівалентний контроль над усіма хостами; розсилати ключі на хости означає розширювати поверхню атаки без виграшу. Окремий ключ на середовище дає криптографічну ізоляцію між серверами |
| Git-репозиторій тягне ЦА (LibGit2Sharp, HTTPS + deploy-токен) | ЦА потрібен вміст для розшифрування; агенту не потрібні ні git-креди, ні ключі |
| Образи тягне агент напряму з registry | Пересилати гігабайти через ЦА безглуздо; креди registry ЦА передає агенту в тимчасовому `DOCKER_CONFIG` на tmpfs |
| Агент викликає `docker compose` CLI, а не реалізує compose через Docker API | Повторювати compose вручну — величезна робота |
| Каталоги стеків монтуються в агент за тим самим шляхом, що й на хості | Шляхи bind-mount'ів резолвить Docker daemon на хості |
| Файлові секрети в `/run/container-forest` (tmpfs хоста) | Не потрапляють на диск; ціна — rehydrate після перезавантаження |
| Env-секрети — свідомий компроміс | Docker зберігає env у конфігурації контейнера на диску (`docker inspect`). Так роблять усі, включно з Portainer; це задокументовано, а не приховано |
| Команди до офлайн-агента не ставляться в чергу | `restart`, виконаний через години, гірший за помилку |
| Авторизація — лише в ЦА, як Decorator навколо команд | Одна перевірка для панелі й бота; обійти через інший інтерфейс неможливо |
| Три окремі операції: restart / redeploy / redeploy with pull (+ окремо down) | Portainer змішує їх в одну кнопку, це головне джерело скарг на нього |
| Веб-панель — окремий сервіс: статична SPA у nginx, nginx проксює `/api` і `/hubs` на ЦА | Same-origin → cookie `SameSite=Strict` і WebSocket без CORS; Node-рантайм не потрібен |
| React + Vite + TanStack Router + TanStack Query | Типізовані маршрути й search params, інтеграція loader'ів із кешем Query |
| UI — shadcn/ui на Tailwind CSS і Radix UI, іконки Material Symbols | Tailwind потрібен у будь-якому разі; компоненти shadcn лежать у репозиторії й правляться під наші екрани, доступність (фокус, клавіатура, ARIA) дає Radix. Mantine / MUI / Ant Design відкинуто: власний вигляд і стилі, MUI і Ant — ще й CSS-in-JS і власні форми, що конфліктують із React Hook Form |
| Discord-бот — окремий .NET-застосунок, говорить із ЦА по gRPC | Сервісний токен бота + Discord ID користувача (on-behalf-of); права перевіряє ЦА |
| Секрети в БД ЦА (креди registry, пізніше git-токени й age-ключі) шифруються ASP.NET Core Data Protection, key ring у `DataProtection:KeyDirectory` (ADR-0003) | Готові ротація ключів і автентифіковане шифрування; власний формат шифротексту з master key довелося б писати й тестувати самим |
| Креди registry прив'язані до середовища, агент отримує лише ті, що потрібні образам стеку | Editor середовища фактично root на хості й може прочитати все, що отримує агент; креди інших середовищ до нього не потрапляють |
| SQLite для MVP | Підтримка ще й PostgreSQL означає два набори міграцій EF Core |
| Системні стеки (ЦА, агент) оновлюються через одноразовий helper-контейнер | Агент, що робить `compose up` власного контейнера, вбиває себе посеред команди |

## Відкинуті альтернативи (не пропонувати повторно без нових аргументів)

- **FUSE-том із секретами** (початкова ідея №5 з тір-листа). FUSE усередині контейнера вимагає `SYS_ADMIN` і `/dev/fuse` на кожному контейнері. Правильна форма — Docker volume plugin, але і вона має мало переваг над ін'єкцією при старті, бо більшість застосунків не перечитують конфіг. Аналоги (`docker-volume-keywhiz`) закинуті. Нормального FUSE-біндингу для .NET немає.
- **ЦА підключається до Docker API хостів по TCP.** Замінено агентами.
- **Агент сам клонує git і розшифровує секрети.** Ключі й креди розповзлися б по хостах.
- **Blazor.** Команда обрала React-SPA окремим сервісом.
- **Next.js.** SSR не потрібен дашборду за логіном; зайвий Node-сервер і плутанина server/client components.
- **Vue / Angular.** Розглядалися (Vue — найнижчий поріг входу, Angular — найближчий до C#/ООП), обрано React.
- **Redux.** Серверний стан живе в TanStack Query, URL-стан у Router.
- **Власна реалізація логіну.** Хешування паролів і сесії — ASP.NET Core; оцінюється шар авторизації, а не логін.
- **Складний RBAC у стилі Portainer BE з явними заборонами.** Ефективна роль = максимум із ролі на середовищі й ролі на стеку.

## Вимоги курсу (ООП, 2026–2027)

**Контракти й доменні сутності — Петренко Б. О.** (рішення команди): `.proto`, REST DTO, події SignalR і `Aggregator.Domain` (включно з `User` і ролями) проєктує й зараховує собі він. Йому ж належить уся ієрархія команд у ЦА (`IContainerCommand`, `ContainerCommand`, конкретні команди, декоратор `AuthorizedCommand`). Бояр В. О. реалізує виконання цих дій на агенті: обробники `IAgentCommandHandler` і роботу з Docker. Інші учасники реалізують логіку поверх цього у своїх зонах. Правило стосується ядра моделі; доменну сутність, яку учасник спроєктував і написав під свою задачу (як креди registry в PR #21 — Бояр В. О.), зараховують її автору, а Петренко Б. О. переглядає її на рев'ю.

Кількості **рахуються для кожного учасника окремо**: кожен елемент приписується одному студенту, двом зараховувати не можна (формулювання умови, прочитання варто підтвердити у викладача). Кількості орієнтовні.

**Лаба 1 — базові ідеї ООП (C#):**
- ≥ 9 класів (або подібних типів), ≥ 15 полів, ≥ 25 нетривіальних методів.
- Тривіальними вважаються геттери/сеттери, що лише читають/пишуть поле, і конструктори, що лише ініціалізують поля. Тому команди мають містити реальну логіку: перевірку стану, таймаути, повтори, аудит.
- ≥ 2 ієрархії успадкування, одна з них ≥ 3 класів.
- ≥ 3 незалежні випадки поліморфізму, серед них хоча б один статичний (generics) і хоча б один динамічний. Для кожного має бути клієнтський код, що працює через поліморфний інтерфейс.
- Доцільна інкапсуляція; де доречно — абстрактні класи й інтерфейси.
- Потрібна точна кількість елементів кожного типу з переліком → `CONTRIBUTIONS.md`.

**Лаба 2 — GUI (веб-панель):**
- ≥ 4 екрани, ≥ 20 елементів керування, ≥ 1 контейнерний елемент (таблиця, список, дерево), ≥ 10 обробників подій.
- Логіка окремо від GUI.
- **Discord-бот не зараховується** (боти в месенджерах умова прямо відносить до «екзотичних» інтерфейсів). Тому учасник, відповідальний за бота, теж робить екрани панелі.

**Лаба 3 — зовнішні бібліотеки:**
- Бібліотеки не зі стандартної бібліотеки мови; не Qt і не фреймворки для unit-тестів.
- EF Core зараховується: окремий пакет з реальними альтернативами (Dapper, linq2db, NHibernate). ASP.NET Core і `Microsoft.Extensions.*` — частина платформи, не зараховуються. Інші пакети Microsoft (ASP.NET Identity тощо) оцінювати окремо.
- У репозиторії чітко вказати, які бібліотеки і які їхні можливості використано.
- Бібліотеки, на відміну від класів, **не закріплюються за одним учасником** (рішення команди): кожен, хто працював із бібліотекою, описує власне використання в `CONTRIBUTIONS.md` і пише власний розділ ретроспективи, навіть якщо його робота не потрапила в коміти.
- Ретроспектива за списком питань з умови (задачі, чому саме ця бібліотека, документація, проблеми, плюси/мінуси, що змінили б, використані ресурси) → `docs/retro/<бібліотека>.md`, окремий розділ на кожного учасника, вести в процесі.
- Кандидати: Docker.DotNet, Discord.Net, Grpc.AspNetCore / Grpc.Net.Client, LibGit2Sharp, YamlDotNet, Quartz.NET, Polly, FluentValidation, Otp.NET, TanStack Query, TanStack Router, React Hook Form, Zod, Monaco Editor, xterm.js.

**Загальні вимоги курсу** (для всіх завдань; у першому семестрі — за додаткові бали, крім позначених):
- **Використання LLM обов'язково вказати** й розуміти весь код, хто б його не написав; відповідальність за помилки — на тих, хто здає. Опис — `docs/ai-usage.md`.
- Unit-тести: обов'язкові для претендентів на «відмінно» / 90+ балів, у другому семестрі — для всіх.
- Документація з коментарів (Doxygen-подібна), бажано на GitHub Pages з генерацією в GitHub Actions: у другому семестрі обов'язкова. У нас — DocFX (`docfx.json` у корені, workflow `Docs`); сайт збирається з вихідного коду, тож `GenerateDocumentationFile` і попередження CS1591 не потрібні.

- Обраний стиль коду з посиланням у README (`.editorconfig`), форматування за ним.
- У репозиторії вказати тему й реалізовані вимоги (основні й додаткові); чужий код — з точним посиланням на джерело.

**Навчальний проєкт:**

## Технічні домовленості

### Бекенд (.NET)

- Доменні класи називаються `DockerEnvironment` (не `Environment`: конфлікт із `System.Environment` через неявний `using System`) і `GitRepository` (не `Repository`: плутається з патерном Repository).
- Домен не читає годинник сам: методи приймають `DateTimeOffset now`. Ідентифікатори — `readonly record struct` над `Guid` v7 з інтерфейсом `IStronglyTypedId<TSelf>`.
- Тести — xUnit v3 на Microsoft.Testing.Platform (увімкнено в `global.json`): `dotnet test --solution ContainerForest.slnx`. Проєкти тестів у `tests/`, структура повторює `src/`.

Команда без обробника (зокрема невідомий агенту варіант `oneof`, що парситься як `BodyCase.None`) — `ERROR_CODE_UNSUPPORTED`. `CommandError.message` показується в панелі: читабельний текст без деталей винятків; деталі — у лог агента.

Команда реєструється синхронно до першого `await`, а сесія читає наступне повідомлення лише після цього, тож `CancelRequest` не випереджає свою ціль. Скасований деплой не видаляє `.prev` секретів.
- ЦА надсилає `CancelRequest` у `AgentSession.RequestAsync`, коли перестає чекати результат (тайм-аут або скасування викликача) і сесія жива. Це best effort з власним тайм-аутом запису 5 с: помилка надсилання не підміняє `AgentTimeoutException`. Без цього compose після 15-хвилинного тайм-ауту деплою й далі змінював би стек.
- Агент використовує форк `Docker.DotNet.Enhanced` (Testcontainers), не закинутий оригінал. Клієнт — `new DockerClientBuilder().Build()`: endpoint як у docker CLI (`DOCKER_HOST` → поточний контекст → типовий сокет). Власний таймаут клієнта (100 с) вимкнено, бо ЦА дозволяє час зупинки до 5 хв; кожен виклик має свій бюджет у `DockerDotNetGateway`.

База — `mcr.microsoft.com/dotnet/runtime:10.0` (Ubuntu 24.04, не Debian): у неї ставляться `docker-ce-cli` і `docker-compose-plugin` з apt-репозиторію Docker, дистрибутив береться з `ID` в `/etc/os-release`. `WORKDIR /app` обов'язковий: без нього content root — `/` і `appsettings.json` не читається. Агент працює від root, бо gid сокета Docker різний на різних хостах.
- `docker compose` запускати через `ProcessStartInfo.ArgumentList` (без shell). Env-секрети передавати в `psi.Environment`, не в `.env`-файл.
- Операції зі стеками: `restart` = `docker compose restart`; `redeploy` = `docker compose -p <stack> -f compose.yaml up -d --remove-orphans --pull missing --wait`; `redeploy with pull` = те саме з `--pull always`. Агент додає глобальні `--ansi never --progress plain`, щоб кожен рядок виводу йшов у лог деплою текстом. Аргументи будує лише `ComposeInvocation` (фабрики `Up`/`Restart`/`Down`); процес запускає `DockerComposeCli` без shell, з тайм-аутом `Agent:ComposeTimeout` (15 хв) і вбиває дерево процесів при скасуванні. Змінні `CF_*` агента в процес compose не передаються: compose-файл міг би підставити їх у контейнер.
- Одна операція на стек за раз (`StackLocks`): друга отримує `ERROR_CODE_BUSY`, а не чекає в черзі. `RestartStack` і `DownStack` для стеку без каталогу — `ERROR_CODE_NOT_FOUND` (compose для неіснуючого проєкту мовчки повертає 0).
- Креди registry: ЦА надсилає `RegistryAuth` лише для хостів образів стеку (для образу з `${VAR}` або з `extends` — усі креди середовища); ключ Docker Hub у config.json — `https://index.docker.io/v1/` (`RegistryHost.ConfigKey`). Агент пише `config.json` у `<SecretsDirectory>/.docker-config/<guid>` (0700/0600), передає `DOCKER_CONFIG` процесу compose і видаляє каталог після нього. Зі своїм `DOCKER_CONFIG` CLI не бачить контекстів користувача, тому працює з типовим сокетом.
- У пакеті `DeployStack` compose-файл стеку завжди називається `compose.yaml` і лежить у корені каталогу стеку, хоч як би він звався в репозиторії (`StackBundle.ComposeFileName`). Агент передає його через `-f compose.yaml`, тож інші compose-файли в каталозі (зокрема `compose.override.yaml`) не підмішуються.
- `RestartStack` і `DownStack` виконувати як `docker compose -p <stack> restart|down --timeout <N>` **без `-f`**, з робочим каталогом `StacksDirectory`, а не каталогом стеку. Так compose не читає файл і не вимагає env-змінних, яких на диску немає; з `-f` або без `-p` у каталозі стеку команда падає на обов'язкових змінних `${VAR:?}` (перевірено на Compose 5.5.1). Env лишається в конфігурації контейнерів.
- SOPS викликати бінарником, ключ передавати через змінну `SOPS_AGE_KEY` дочірнього процесу, вміст — через stdin. Приватні ключі в БД ЦА шифруються через `ISecretProtector` (ADR-0003) з окремим `SecretPurpose`.
- Каталог стеку не замінюється (ADR-0004): контейнери монтують шляхи в ньому, і заміна каталогу лишила б їх на старій копії з даними. `StackFileStore` готує кожен файл у `<name>.tmp` і перейменовує поверх цільового; файли попереднього пакета, яких немає в новому, видаляються за маніфестом `<StacksDirectory>/<name>.manifest.json` (лежить поза каталогом стеку, щоб контейнер не міг його переписати). Файли, створені контейнерами, не чіпаються. Попередня версія пакета — копія в `<name>.prev`.
- Агент працює від root, а контейнер може створити в змонтованому каталозі посилання на `/`: перед записом, копіюванням і видаленням перевіряється, що між каталогом стеку й файлом немає символьних посилань. Каталог на хості там, де в пакеті файл, — `StackFileConflictException` (`ERROR_CODE_COMMAND_FAILED`) до будь-яких змін.
- Файли з `StackFile.secret = true` пишуться в `/run/container-forest/<stack>/<path>` (каталог стеку 0700; замінюється цілим каталогом `.tmp` → поточний → `.prev`, бо контейнери туди не пишуть), а в каталозі стеку за тим самим відносним шляхом лежить символьне посилання на них. Compose-файл у репозиторії посилається на секрет звичайним відносним шляхом (`file: ./secrets/db_password`), а Docker розв'язує посилання на хості: шляхи на хості й в агенті однакові. Вміст секретів на диск не потрапляє; після перезавантаження хоста посилання порожні до rehydrate. `.prev` із секретами видаляється одразу після успішного `compose up`, після `DownStack` — секрети стеку. На Windows (лише розробка) секретні файли можна писати прямо в каталог стеку з попередженням у лозі.
- Webhook GitHub/Gitea: перевірка HMAC через `CryptographicOperations.FixedTimeEquals`, лише постановка в чергу; деплой виконує фоновий сервіс.
- Cookie-автентифікація для API повертає 401/403 замість редіректу на логін. За reverse proxy — `UseForwardedHeaders` з `XForwardedProto`.
- Kestrel: окремий порт для gRPC (HTTP/2), окремий для REST/SignalR. Локально 5081 і 5080 на `localhost`; у `appsettings.json` — `+`, розробка перекриває це в `appsettings.Development.json`, щоб dev-ендпоінти не були видні в мережі.
- `/api/dev/*` — тимчасові ендпоінти, мапляться лише в `Development`. Там, крім cookie, діє схема автентифікації `DevUser`: заголовок `X-Dev-User` називає користувача без пароля (будь-якого, створеного через `/api/users` або bootstrap). Схемою за замовчуванням у `Development` є policy-схема `DevOrCookie` (`ForwardDefaultSelector`): є заголовок — `DevUser`, немає — cookie; поза `Development` — лише cookie. Прибрати разом зі схемою, коли з'явиться справжній API панелі.
- **Автентифікація й авторизація розділені одним договором:** будь-яка схема (cookie логіну, dev-заголовок, пізніше бот) кладе `UserId` у claim `ClaimTypes.NameIdentifier`; `ClaimsCurrentUser` читає його як `ICurrentUser`, а сервіси `Application` отримують користувача лише через `CurrentActor` (немає користувача — 401, деактивований — 403). Логін (ASP.NET Identity, cookie `cf_session`, `/api/auth/*`) — зона Денисенко Л. В.; контракт — `Api/Contracts/AccountContracts.cs`.
- **Вхід за паролем.** Паролі, lockout і security stamp — в ASP.NET Identity: `AccountUser : IdentityUser<Guid>` (`Infrastructure/Accounts`) з тим самим id, що й доменний `User`; `AggregatorDbContext` успадковує `IdentityUserContext<AccountUser, Guid>` (таблиці `AspNetUsers*`, без таблиць ролей). Зовнішнього ключа `AspNetUsers` → `Users` немає: EF не з'єднує `Guid` із `UserId`; обліковий запис створюється разом із доменним користувачем в одному `SaveChanges` (`UserManager.CreateAsync` зберігає контекст). Користувачі, створені колись через видалений `/api/dev/users`, облікового запису не мають: його створює скидання пароля адміністратором.
- **Керування користувачами** (`/api/users/*`, контракт — `Api/Contracts/UserContracts.cs`): `UserManagementService`, усе лише для адміністраторів. Облікові записи Identity сервіс змінює лише через порт `IAccountStore` (`IdentityAccountStore`); кожна зміна облікового запису зберігає контекст разом із доменними змінами. Пароль перевіряється політикою до зміни хешу, щоб невдалий пароль не лишив облікового запису без пароля.
  - Зміни користувача — ієрархія `UserAccountAction` (Command): перевірка → дія → завершення сесій (`EndsSessions`). `AdministratorRemovingAction` (деактивація, зняття прав адміна) не дає прибрати останнього активного адміністратора (409). Деактивація, зняття прав адміна й скидання пароля завершують сесії користувача; перейменування — ні (`SetUserNameAsync` Identity міняв би security stamp, тому ім'я змінюється через `UpdateAsync`).
  - Ролі: одна на область (середовище або стек), друга — 409; стек іншого середовища й чуже призначення — 404.
  - Політика — `AccountPolicy`: пароль від 12 символів без правил про склад, lockout після 5 невдалих спроб на 15 хв. Решту NIST SP 800-63B перевіряють правила `PasswordRule` (`IPasswordValidator` Identity, `Infrastructure/Accounts/PasswordRules.cs`): не довше 128 символів, без повторів і послідовностей (`aaaa…`, `1234…`, `qwerty…`), без імені користувача й назви системи. Код помилки правила починається з `Password`: так `IdentityAccountStore` відрізняє відхилений пароль від інших помилок Identity. Відхилений пароль — `PasswordRejectedException` → 400 з `errors` у problem details.
  - `PasswordSignIn`: невідоме ім'я, неправильний пароль, lockout і деактивований користувач — однаковий 401; для невідомого імені все одно рахується хеш (decoy), щоб час відповіді не видавав наявні імена.
  - Cookie `cf_session`: HttpOnly, `SameSite=Strict`, `Secure` — `Always`, у `Development` — `SameAsRequest`; `RememberMe` — постійна cookie, інакше сесійна. Security stamp перевіряється на кожному запиті (`ValidationInterval = 0`): зміна пароля завершує інші сесії одразу, поточна перевидається (`RefreshSignInAsync`). Ціна — запит до БД і нова cookie на кожну відповідь.
  - Перший адміністратор: `AdminBootstrapper` після міграцій, якщо в базі немає жодного користувача, створює його з `CF_BOOTSTRAP__ADMINUSERNAME` / `CF_BOOTSTRAP__ADMINPASSWORD` (задаються разом або жодна, `ValidateOnStart`). Пароль не логується; без змінних і без користувачів — попередження в лозі.
- **Discord-бот:** контракт — `src/Contracts/bot/bot.proto` (пакет `bot`), бот лише клієнт. Сервісний токен у metadata `x-bot-token` (у ЦА — лише хеш), Discord ID користувача — поле кожного запиту. ЦА перевіряє права прив'язаного користувача так само, як для панелі; помилки — коди статусу gRPC, для `UNAUTHENTICATED` причину уточнює трейлер `x-cf-reason` (`invalid-bot-token` / `account-not-linked`).
- Токен бота задається конфігурацією, а не видається ендпоінтом: він рівносильний адмінському доступу, тож випустити його має лише той, хто має доступ до сервера ЦА, а не будь-яка адмінська сесія в браузері. ЦА: `CF_BOTGATEWAY__TOKENHASHES__0` (`__1`, …) — SHA-256 токена, 64 hex-символи в нижньому регістрі, як `SecretToken.Hash`; перевірка — `SecretToken.Matches`; неправильний формат хешу зупиняє старт (`ValidateOnStart`). Бот: `CF_BOT__SERVICETOKEN`. Генерація: `openssl rand -hex 32`, хеш — `printf '%s' "$TOKEN" | sha256sum`. Без жодного хешу `BotGateway` відхиляє всі виклики (`invalid-bot-token`). Кілька хешів — для ротації без простою: додати новий → перезапустити ЦА → перевести бота → прибрати старий. Токени в БД — лише коли знадобиться кілька ботів або ротація з панелі; контракт від цього не зміниться.
- Прив'язка Discord-акаунта — доменна сутність `DiscordLink` (таблиця `DiscordLinks`, один запис на користувача, Discord ID унікальний), а не зовнішній логін ASP.NET Identity: бот не залежить від Identity, і прив'язка працює ще до логіну. В альфі — одноразовий код з панелі (`/api/me/discord/link-code`, 8 символів без схожих літер, 10 хвилин, зберігається лише хеш) і `/link <код>` у боті (`LinkAccount`). В остаточній версії основний спосіб — вхід через Discord OAuth2: після нього користувача шукати за `DiscordLink`, а команда лишається альтернативою. Повторна прив'язка того самого Discord-акаунта переносить її на нового користувача.
- `BotGatewayService` (порт gRPC той самий, що для агентів): `BotGatewayInterceptor` перевіряє токен і перекладає винятки на коди статусу з `bot.proto`; кожен виклик від імені користувача кладе його `UserId` у `HttpContext.User` (claim `NameIdentifier`), тож далі працюють ті самі сервіси й перевірки прав, що й для панелі.
- Бот звертається до ЦА лише через `IForestClient` (`src/DiscordBot/Forest`); помилки — нащадки `ForestException`, їхній текст показується користувачу. Недоступний ЦА і `invalid-bot-token` — `ForestUnavailableException`: у лог, користувачу загальне повідомлення. Статус, створений самим клієнтом gRPC (є `Status.DebugException`), означає, що до ЦА не дійшли, навіть якщо код `Unavailable` чи `Internal`. Тести бота генерують серверну частину `bot.proto` і підключають бота через `extern alias bot`, щоб згенеровані типи не конфліктували.
- Команди бота — нащадки `BotCommand<TArgs, TResult>` (`src/DiscordBot/Commands`): шаблонний метод defer → виклик ЦА → форматування → помилка як відповідь. Discord.Net бачить лише модуль `ForestModule` і адаптер `DiscordInteraction` (`ICommandInteraction`), тож логіка команд тестується без Discord. Усі відповіді ephemeral: відкладена відповідь зберігає видимість, з якою її відклали, а списки середовищ і контейнерів не мають потрапляти в канал, де є люди з меншими правами. Відповіді надсилаються з `AllowedMentions.None`, текст ззовні екранується (`Markdown.Escape`). Автодоповнення не можна відкласти: бюджет 2 с, помилка — порожній список. `Development` реєструє команди на тестовому сервері (`CF_DISCORD__DEVGUILDID`, обов'язковий), інші оточення — глобально.
- **Сповіщення** доставляються в Discord через живого бота, а не webhook'ом каналу: бот тримає server-stream `WatchNotifications` і звітує `ReportDelivery` про кожне (`bot.proto`). Так URL webhook'ів (фактично секрети) ніде не зберігаються, а бот може додати кнопки до повідомлення, наприклад «Restart» під упалим контейнером, і натискання піде звичайним `ControlContainer` з правами того, хто натиснув. Ціна: без підключеного бота сповіщення не доставляються; вони лишаються `Pending` і надсилаються після підключення, а старші за годину — `Expired`.
- Домен сповіщень (`Domain/Notifications`): `NotificationChannel` (Discord-канал), `NotificationRule` (які події, з якої області: уся система, середовище або стек; `Matches`), `NotificationEvent` (одна подія з рівно одним видом) і `Notification` (запис історії: Pending → Delivered | Failed | Expired). Канали й правила керуються лише адміністраторами: Discord-канал можуть читати люди без жодної ролі. Історія не має зовнішніх ключів на правила й канали, щоб переживати їх видалення. Диспетчер сповіщень, `WatchNotifications`/`ReportDelivery` у `BotGatewayService` і джерела подій (спершу результати деплоїв, потім `ContainerEvent` агента) — зона Синенка Д. В.
- Сповіщення в ЦА: джерело подій викликає `NotificationDispatcher.DispatchAsync(event, summary)`; диспетчер створює одне `Notification` на канал (від найконкретнішого правила, що збіглося), зберігає й будить потік бота через `NotificationFeed` (singleton, один підписник: новий `WatchNotifications` завершує старий з `Aborted`). Деплої — через `IDeploymentObserver` (`DeploymentNotifier`), який `DeployPipeline` викликає після збереження результату; спостерігач сам логує свої помилки й не кидає. `Notification.Details` — знімок деталей події (`DeploymentNotificationDetails`: коміт, помилка), зберігається JSON-колонкою (`NotificationDetailsConverter`), щоб сповіщення, доставлене після перепідключення бота, було тим самим. Канал і назву середовища потік бере на момент надсилання: переміщений канал отримує й старі сповіщення, а сповіщення видаленого чи вимкненого каналу стають `Failed`.
- `BotGatewayInterceptor` перевіряє токен для всіх видів викликів, включно з потоковими: базовий `Interceptor` пропускає їх без перевірки.
- Бот: `NotificationWatcher` (hosted service) чекає `Ready` Discord, тримає потік через `INotificationSource` (`GrpcNotificationSource`) і перепідключається з backoff (1 с → 60 с, jitter); кожне сповіщення публікує `INotificationPoster` (`DiscordNotificationPoster`, embed з `AllowedMentions.None`) і звітує результат. Відмова Discord (немає каналу, бракує прав) — `delivered = false` з підказкою для панелі; невдалий звіт лише логується: ЦА надішле сповіщення знову в наступному потоці. Канал бота шле HTTP/2 keepalive-пінги, бо потік може мовчати годинами.
- Середовища створюють і видають enrollment-токени лише адміністратори. Списки середовищ і контейнерів фільтруються за `AccessPolicy`; недоступне середовище — 404, а не 403, і до агента запит не йде.
- Контейнер із запиту шукається `ContainerLookup` як у docker CLI: повний id, потім точне ім'я, потім унікальний префікс id (неоднозначний префікс — 409).
- Дії з контейнерами йдуть лише через `ContainerCommandService`: (1) середовище, яке користувач не бачить, — 404 ще до звернення до агента, щоб не розкривати його існування; (2) `ListContainers` дає стан і мітку стеку; (3) `AuthorizedCommand` перевіряє право на стеку, а для контейнерів поза керованими стеками — на середовищі; (4) `ContainerCommand` перевіряє стан і надсилає команду. Контейнери системних стеків можна лише запускати: stop/restart обірвали б з'єднання, яким іде команда.
- Кожна операція з БД у довгому gRPC-виклику `Connect` — у власному DI-scope: один `DbContext` на години виклику тримав би застарілі сутності.
- Результат команди від агента приходить у `AgentSession.Complete` за `request_id`, прогрес (`CommandProgress`) — у колбек `onProgress` того самого запиту. Події контейнерів і логи поки ігноруються, споживачі з'являться разом із live-оновленнями й стрімінгом логів.
- **Пайплайн деплою:** кроки `IDeployStep` реєструються в `AddApplication` у порядку виконання: `GitFetchStep` → `ValidateComposeStep` → `BuildBundleStep` → `SendToAgentStep`. Новий етап (SOPS, креди registry) — новий клас і рядок реєстрації, `DeployPipeline` не змінюється. Результати кроків передаються через `DeployContext`; `DeploymentFailedException` — помилка, яку бачить користувач, решта винятків ховається за «Internal error» і йде в лог ЦА.
- Деплой лише ставиться в чергу (`IDeploymentQueue`, 202 Accepted), виконує його `DeploymentWorker` у власному DI-scope, до `Deployments:MaxConcurrentDeployments` паралельно. Один незавершений деплой на стек (409). До офлайн-агента деплой не ставиться (503). Після рестарту ЦА незавершені деплої позначаються Failed, а не відновлюються.
- **Restart і down стеку** (`Application/Stacks/StackCommand.cs`, `StackCommandService`): ієрархія `StackCommand` → `RestartStackCommand`, `DownStackCommand`. Право — як у `RolePermissions.RequiredFor`: restart — Operator, down — Editor; невидимий стек — 404 до звернення до агента; системний стек — 409 (`EnsureAllows`, `RequiresUpdateHelper`); незавершений деплой стеку — 409, бо `ERROR_CODE_BUSY` агента покриває лише час, коли compose уже працює. Тайм-аут зупинки — на кожен контейнер, 0–300 с, типово 10 с. Виконуються синхронно, без черги й без запису в історію деплоїв: вивід compose (останні 1000 рядків) повертається у відповіді. Помилка самого compose (`COMMAND_FAILED`, `TIMEOUT` агента) — результат із `error` і виводом (HTTP 200), решта помилок агента — problem details (`NOT_FOUND` для стеку, якого агент не розгортав, — 404, `BUSY` — 409). Запит до агента йде без токена викликача: закрита вкладка не має обривати `down` посередині, лишивши частину контейнерів зупиненими; ЦА чекає `AgentGateway:StackCommandTimeout` (16 хв, на хвилину довше за `Agent:ComposeTimeout`). Успішний down скидає `DeployedCommit` і `DeployedAt` (`Stack.RecordTakenDown`): контейнерів цього коміту більше немає, хоча файли стеку лишаються на хості; невдалий down їх не чіпає, бо частина контейнерів може працювати. Бот не пропонує такий стек в автодоповненні. Ендпоінти поки dev: `POST /api/dev/stacks/<id>/restart|down?timeoutSeconds=N`. Бот викликає те саме через `ListStacks` і `ControlStack` у `bot.proto` (стек — за назвою в середовищі; невідома, некоректна назва й невидимий стек — однаковий `NOT_FOUND`); `can_restart` і `can_take_down` для системного стеку завжди false. Команди `/stack-restart` і `/stack-down` показують кінець виводу compose в блоці коду (`ReplyFormatter.WithOutput`: останні рядки в межах 2000 символів, ` ``` ` у виводі розривається пробілом нульової ширини); дедлайн виклику — `Bot:StackActionTimeout` (14 хв, менше за 15 хв токена взаємодії Discord), а коли бот перестає чекати, compose усе одно доходить до кінця.
- Лог деплою — рядки `DeploymentLogLine` у таблиці `DeploymentLogLines`, до 5000 рядків. Вивід compose з агента збирається під час кроку й копіюється в лог після нього: `Deployment` не потокобезпечний, а колбек прогресу викликається з циклу читання gRPC.
- Git: bare-клон на кожен репозиторій у `Git:CacheDirectory` (типово `git-cache` у робочому каталозі), fetch лише гілки стеку з `Prune`, файли читаються з дерева коміту без checkout. У пакет іде каталог compose-файлу (для compose в корені — увесь репозиторій) у межах `Deployments:MaxBundleBytes` (3 MiB); символьні посилання й сабмодулі пропускаються з попередженням. Репозиторій із токеном поки відхиляється; шифрувати токен — через `ISecretProtector` (ADR-0003).

### Фронтенд

- Шляхи нижче відносно `src/Web`.
- Vite 8, React 19, TypeScript **5.9**, а не 7: `openapi-typescript` підтримує лише TypeScript 5 (TS 7 не має JS API). Версії в `package.json` точні (`--save-exact`), Node — з `.nvmrc`.
- Два tsconfig: `tsconfig.json` для застосунку (без типів Node), `tsconfig.node.json` для `vite.config.ts`. Аліас `@/` → `src/`.
- UI: shadcn/ui (стиль `radix-nova`, `components.json`), Tailwind CSS 4 через `@tailwindcss/vite`, теми — CSS-змінні в `src/styles.css`, шрифт Geist вбудовується в збірку. Компонент додається командою `npm run ui:add -- <назва>` у `src/components/ui`, а не `npx shadcn add` напряму.
- Іконки — Material Symbols (Rounded), не Lucide: shadcn генерує компоненти лише з Lucide, Tabler, HugeIcons, Phosphor, Remix або Radix Icons, тому `ui:add` (`scripts/ui-add.mjs`) після `shadcn add` переводить імпорти `lucide-react` на `@/components/icons` і прибирає `lucide-react` із залежностей. `src/components/icons.ts` зіставляє lucide-назви (`CheckIcon`, `XIcon`, …) з іконками Material; нова іконка, якої там немає, валить typecheck — додати рядок. Іконки компілює в React-компоненти `unplugin-icons` (з `@iconify-json/material-symbols` і `@svgr/core`) під час збірки: у бандл потрапляють лише використані, без шрифту й CDN. Ці файли згенеровані: їх можна правити, але в облік лаби 2 вони нікому не йдуть; зараховуються екрани й власні компоненти поза `components/ui`. Для лаби 3 бібліотеки тут — Tailwind CSS і Radix UI (shadcn — генератор коду, а не бібліотека).
- Доступ до API — `api` з `src/api/client.ts` (`openapi-fetch`, типи з `schema.gen.ts`); `unwrap` перетворює не-2xx на `ApiError` з problem details. На 401 Query не повторює запит.
- Якщо задано `CF_DEV_USER`, dev-сервер додає `X-Dev-User` у проксі (`vite.config.ts`) і панель працює без входу; у коді застосунку dev-автентифікації немає. Екран `/login` (Денисенко Л. В.): React Hook Form + Zod, мутації входу й виходу — `src/api/auth.ts` (вхід прибирає кеш попереднього користувача й кладе відповідь у `meQuery`, вихід прибирає кеш). Помилка 401 — одне повідомлення «Неправильне ім'я користувача або пароль», без підказок про політику паролів. Керування користувачами (`/users`, `/users/$userId`) і власний обліковий запис зі зміною пароля (`/account`) — теж Денисенко Л. В.: мутації — `src/api/users.ts` (кожна інвалідовує `usersQuery.queryKey`, тож оновлюються і список, і картка), стан і фільтр — `src/lib/users.ts`, фільтри списку — у search params. Причини відхилення пароля ЦА (`errors` у problem details) панель показує як є, англійською, під перекладеним заголовком (`PasswordReasons`). `search.redirect` приймає лише шляхи того самого сайту (`/…`, не `//…`), щоб не було open redirect; після входу — `navigate({ href: redirect ?? "/", replace: true })`.

Інлайн-скриптів і стилів з CDN у застосунку не додавати: CSP їх заблокує.

О.): середовище й фільтри (`stack`, `state`, `q`) у search params; без `environment` або з невидимим середовищем `beforeLoad` перенаправляє на перше, зберігаючи фільтри. Доступність кнопок повторює правила `ContainerCommand` ЦА; stop/restart підтверджуються в `AlertDialog` з тайм-аутом 0–300 с, start — одразу. Повідомлення про результат зберігаються як ключ перекладу, а не текст, щоб перемикання мови їх перекладало.

Повідомлення схем Zod — ключі перекладу (`"…" satisfies MessageKey`), перекладаються під час рендеру. Мова: збережена в `localStorage` (`cf-language`) → мова браузера → українська. Тексти помилок ЦА (`detail` у problem details, `CommandError.message`) лишаються англійськими; відомі випадки панель показує власним перекладом за статусом або кодом. Бот поки лише англійською; Discord передає мову користувача (`UserLocale`), тож переклад бота можна додати пізніше.
- Форми — React Hook Form + Zod. Глобальний UI-стан — `useState`/Context; Zustand лише за реальної потреби. Redux — ні.

- TS-клієнт генерується з `src/Aggregator/Api/openapi/*.json` (`openapi-typescript` + `openapi-fetch`). Змінив DTO — перезбери `Api`, закомить JSON і перегенеруй клієнт. Типи подій SignalR пишуться вручну.
- `routeTree.gen.ts` комітиться, руками не редагується.

## Відомі пастки (додатково до docs/architecture.md)

- gRPC обмежує повідомлення 4 МБ за замовчуванням: задати явний ліміт розміру пакета деплою на ЦА і відхиляти більші.
- Reverse proxy перед ЦА має пропускати HTTP/2 для gRPC (у nginx — `grpc_pass`) і мати великі таймаути для довгих стрімів, інакше з'єднання рватиметься кожні 60 с.
- Після перезавантаження хоста Docker піднімає контейнери раніше, ніж агент підключається, тому контейнери з файловими секретами падають до rehydrate. Новий `boot_id` у `Hello` — сигнал для ЦА повторно надіслати секрети.
- LibGit2Sharp з NuGet не підтримує SSH — лише HTTPS.
- Назва стеку: `^[a-z0-9][a-z0-9_-]*\z`, до 63 символів (вимога compose і захист від path traversal). У регулярних виразах валідації — `\z`, а не `$`: `$` пропускає рядок із `\n` у кінці. Кожен `StackFile.Path` — відносний, без `..`, після `Path.GetFullPath` лишається в каталозі стеку.
- Образи з тегом `latest` або без тегу ламають відтворюваність: відкат файлів стеку не повертає попередній образ. `ValidateComposeStep` лише **попереджає** в лозі деплою, а не відхиляє: багато образів публікуються тільки з `latest`, а «redeploy with pull» існує саме для рухомих тегів. Образ із digest (`@sha256:...`) попередження не отримує. `build:` у compose відхиляється.
- Генератор OpenAPI під час збірки (`GetDocument.Insider`) запускає хост **разом із hosted-сервісами**. Тому в `Program.cs` міграції вимикаються, коли entry assembly — `GetDocument.Insider`; інакше збірка створює базу. З тієї ж причини в цьому режимі не підключається Data Protection з файловим key ring (ефемерний провайдер), інакше збірка створює `data-protection-keys/`.
- Key ring Data Protection (`DataProtection:KeyDirectory`, типово `data-protection-keys`) — єдиний спосіб розшифрувати збережені секрети: бекапити разом із базою, у контейнері ЦА монтувати томом. Втрачений key ring — `SecretUnreadableException`, креди треба задати заново.
- SQLite не має типу `DateTimeOffset`: як текст його не можна порівнювати й сортувати в запитах. Усі `DateTimeOffset` зберігаються як `long` (`DateTimeOffsetToBinaryConverter`, конвенція в `AggregatorDbContext`).
- Вирази EF (`ValueConverter`) не можуть викликати `static abstract` члени інтерфейсу напряму — лише через звичайний статичний метод (див. `StronglyTypedIdConverter`).
- xUnit v3 з аналізатором `xUnit1051` вимагає передавати `TestContext.Current.CancellationToken`; у CI це помилка збірки.
- Логи контейнерів можуть містити секрети; маскування в аудиті не рятує від того, що застосунок сам вивів у stdout.
- .NET SDK на машині розробника може не бути: збирати й тестувати можна в контейнері `mcr.microsoft.com/dotnet/sdk:10.0` з каталогом репозиторію, змонтованим у `/src` (тести агента з `/bin/sh` і правами файлів тоді виконуються як на Linux).
- Розробка на Windows: Docker.DotNet підключається через named pipe поточного Docker-контексту (`npipe://./pipe/dockerDesktopLinuxEngine` у Docker Desktop). Якщо Docker вимкнено, підключення чекає 10 с і завершується `TimeoutException`; `/proc/.../boot_id` немає, тому boot_id — час старту системи (`UptimeBootIdProvider`).
- Демонстрація на захисті — на тестовому середовищі, не на робочій інфраструктурі.
- Radix `Select` (shadcn) викликає `onValueChange` не лише на вибір користувача: з поточним значенням під час монтування і з `""`, поки значення не збігається з жодним пунктом (наприклад, до завантаження списку). Обробник, що скидає інші фільтри або навігує, має ігнорувати `""` і незмінене значення, інакше навігація зациклюється або губить search params.
- У `redirect` з `loader` функція `search: (prev) => …` отримує параметри попереднього розташування, а не того, куди йде перехід; перенаправлення зі збереженням параметрів робити в `beforeLoad`, де є `search` цільового маршруту.
- Vite dev-сервер у Linux-контейнері з каталогом, змонтованим із Windows, не отримує подій зміни файлів: після правок його треба перезапускати (або вмикати polling).

## Відкриті питання

- Дедлайни етапів проєкту (альфа, остаточна версія).
- Спитати у викладача на показі лаби 1:
  - чи рахуються кількості в лабах 1–2 на кожного учасника (умова вимагає приписати кожен елемент одному учаснику, але поріг на учасника прямо не названо);
  - чи зараховується ASP.NET Core Identity як зовнішня бібліотека в лабі 3 (окремий пакет Microsoft з альтернативами, як EF Core);
  - чи достатньо `docs/ai-usage.md` і трейлерів `Co-Authored-By` у комітах як вказання використання LLM.
- Reverse proxy для продакшн-розгортання ЦА (Caddy / Traefik / nginx): вирішити разом із прикладом розгортання ЦА. Від нього не залежить код: ЦА працює і за проксі, і з власним TLS (див. «Мови і фреймворки» в `docs/architecture.md`).

Відкладено (не питання, а свідомо не на часі):

- Перехід на .NET 11 (STS) — лише за конкретні фічі, не за строк підтримки.
- mTLS між агентом і ЦА — stretch goal.
