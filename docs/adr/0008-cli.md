# ADR-0008. The `forest` CLI: browser sign-in, the token and the API client

- Status: accepted
- Date: 2026-10-09

## Context

The panel isn't the only way to manage the system: deploying from a script, reading logs in a terminal over SSH, CI. That needs a CLI covering almost everything the panel can do. It authenticates with a personal API token (ADR-0007). Pasting the token by hand is inconvenient: it has to be created in the panel, copied and not lost. The CLI should be able to get a token itself.

Sign-in options considered:

1. **A password in the terminal.** The CLI exchanges a user name and password for a token. Doesn't work for passkeys and Discord sign-in, and the password passes through one more program.
2. **A loopback redirect with the token in the URL** (as older versions of `gh auth login --web` did). The token ends up in the browser's history; doesn't work over SSH.
3. **The device authorization flow (RFC 8628)** (chosen) with a loopback signal: the CLI gets a one-time code, the person approves it in the panel with any sign-in method, and the CLI collects the token by polling. It works over SSH too (`--device`), and locally the browser wakes the CLI at once through `127.0.0.1`.

## Decision

### The sign-in flow

1. CLI: `POST /api/cli/authorizations` with the client's and host's names. The aggregator returns a `deviceCode` (32 random bytes, for the CLI only), a `userCode` (8 characters without look-alike letters, like the Discord link code), the panel page's path, a lifetime (10 minutes) and a polling interval (5 s). Both codes are stored as hashes (`CliAuthorization`).
2. Locally, the CLI listens on `127.0.0.1:<random port>` and opens `<server URL>/cli/authorize?code=<userCode>&port=<port>`. With `--device` the CLI only prints the `/cli/device` URL and the code.
3. The person signs in to the panel (password, passkey, Discord, any way), sees the client, the host, the request's IP and the code to compare with the terminal, picks the token's restrictions (the same as on the *API tokens* screen) and allows or denies. Only a session decides, never a token (`GetSignedInUserAsync`).
4. After the decision the panel sends the browser to `http://127.0.0.1:<port>/done?result=…`: only a "time to poll" signal, with no secret. The panel takes the port from the URL, and the host is always `127.0.0.1`, so the page can't redirect the browser anywhere else.
5. CLI: `POST /api/cli/token` with the `deviceCode` → `Pending` / `SlowDown` / `Approved` (with the token) / `Denied` / `Expired`. **The token is created only at this moment** and returned once; between approval and issuing, the database holds only the chosen restrictions, not a token. An unknown code is `Expired`, like an expired one.

Protection: unauthenticated endpoints and those that accept the short `userCode` are rate-limited per address (ASP.NET Core's `RateLimiter`: 10 starts, 30 polls and 20 code lookups per minute); there are at most 500 open requests in the system, and expired ones are deleted when new ones arrive. The device flow's known weakness is phishing (an attacker sends their own link): the page shows the host, the address and the code, and explicitly asks to deny a request the person didn't start.

### The client

- **.NET 10 + System.CommandLine, NativeAOT**: the same language as the rest of the backend, one binary with no runtime (linux/win/mac, x64/arm64). Go or TypeScript would mean another language and another CI job.
- **Kiota generates the API client** from the aggregator's committed OpenAPI document, like `schema.gen.ts` for the panel; CI checks it's up to date. Kiota is AOT-compatible and supports OpenAPI 3.1, which ASP.NET Core 10 generates. The generated models are nullable and mutable, so the CLI works with them through its own adapter (`IForestApi`), not directly.
- **Credentials:** `--token` / `--token-file` (`-` is stdin) and `--url` → `CF_TOKEN` / `CF_URL` → the context `--context` / `CF_CONTEXT` → the current context in `$XDG_CONFIG_HOME/container-forest/config.json` (else `~/.config/…`, `%APPDATA%` on Windows; directory 0700, file 0600, written atomically). Contexts let you work with several installations. `forest logout` revokes the token on the server (`DELETE /api/me/tokens/current`) and forgets it.
- The CLI doesn't change the password, passkeys, tokens or Discord linking: only a panel session can (ADR-0007).
- **No request retries.** Kiota retries failed requests by default, POST included; retrying a deployment would queue it twice, so `RetryHandler` is removed. Any failed response becomes a `ServerProblemException` with the aggregator's `title`/`detail` (`ProblemDetailsHandler`), whether or not the OpenAPI document describes the status.
- **The token never crosses the network in plain text:** `http://` is allowed only for addresses on this machine. A context's token is sent only to that context's server, never to a URL from `--url` or `CF_URL`.
- **Destructive actions** (`stack down`, `stack remove`, `env remove`, `env revoke-agent`, `env key remove`) do nothing without `--yes`.
- **Output:** the result goes to stdout (a table, or `-o json` with the server's JSON), progress messages to stderr. Exit codes: 0 success, 1 the operation failed, 2 a wrong invocation, 3 no credentials or the server rejected them, 4 no permission or not found, 5 the server or the agent is unreachable, 130 Ctrl+C.
- **Distribution:** NativeAOT binaries for linux-x64, linux-arm64, osx-arm64 and win-x64 with `SHA256SUMS` in GitHub Releases under the `cli-v<version>` tag (the `CLI` workflow; since 0.8.0, in the `vX.Y.Z` release of the system's shared version, see docs/development.md, "Releases"); no `dotnet tool` is published, since it would need the .NET runtime.
- **Secrets for commands** (passwords, git tokens, registry credentials) come only from stdin or no-echo input, never from an option: otherwise the process list and the shell history keep them.
- **The command framework:** the hierarchy `ForestCommand` → `EnvironmentCommand` (`--env`, the context's default environment or the only visible one) → `StackCommand` (a stack by name or id), and `CommandGroup` for groups (Composite); `CliHost` runs a command, resolves credentials and turns errors into messages and exit codes.

## Consequences

- Any way of signing in to the panel automatically works for the CLI too: the CLI knows nothing about passwords, passkeys or Discord.
- A new group of unauthenticated endpoints (`/api/cli/authorizations`, `/api/cli/token`), the first with rate limiting in the aggregator.
- The pages `/cli/authorize` and `/cli/device` in the panel; the first is an ordinary route behind sign-in, so after signing in the person comes back to it with the same code.
