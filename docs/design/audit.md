# Журнал аудиту

Шляхи `Domain/…`, `Application/…`, `Infrastructure/…`, `Api/…` — відносно `src/Aggregator`, шляхи панелі (`src/features/…`, `src/components/…`) — відносно `src/Web`.

- **Журнал аудиту** (`Domain/Audit`, `Application/Audit`, `Api/Contracts/AuditContracts.cs`; зона Денисенко Л. В.): `AuditEntry` — хто (`AuditActor`: id й ім'я на той момент, канал `Panel`/`ApiToken`/`Bot`/`Anonymous`, id токена, IP; у бота — без IP), що (`AuditAction`, розділ `AuditCategory` виводиться з дії), над чим (ієрархія `AuditTarget`: користувач, роль, токен, середовище, стек, контейнер за ім'ям, файл за шляхом; ціль дає середовище й стек для фільтра) і результат (`Succeeded`, `Denied`, `Failed`). Імена копіюються, зовнішніх ключів немає: журнал переживає перейменування й видалення. Секретів у записі немає (інваріант 6): ні паролів, ні токенів, ні вмісту файлів, лише назви й шляхи; причина невдачі — повідомлення відомих винятків (`AuditOutcomes.Of`), невідомі — «Internal error.».
  - Сервіси пишуть через `IAuditTrail`: `RunAsync(new AuditDraft(дія, ціль), work)` виконує дію і записує результат за винятком (`AccessDeniedException` — `Denied`, решта — `Failed`, `UnauthenticatedException` не записується) або за `draft.Fail(...)` (дія повернулася, але не вдалася, як compose з помилкою); `work` уточнює `draft.Target` і `Details`, коли завантажить об'єкт. `RecordAsync` — для відомого результату; для запитів без сесії (вхід, зворотний виклик Discord, `/link` бота) актора задає `AuditPerson`. Нова дія, яку треба бачити в журналі, — нове значення `AuditAction` (зберігається назвою, тож порядок не важливий), випадок у `AuditActions.CategoryOf`, переклад у панелі (`audit.actions`).
  - `AuditLog.AppendAsync` пише у власному `DbContext` нового scope, без токена скасування: відмовлена чи невдала спроба записується, а напівзроблені зміни запиту — ні; закрита вкладка не губить запис. Ціна — запис не в одній транзакції з дією: дія, збережена перед збоєм запису журналу, лишається без запису (помилка — у лог ЦА, дію вона не ламає).
  - Що записується: вхід паролем, passkey і Discord (невдалий — з наданим ім'ям і причиною), вихід, зміна власного пароля, прив'язка й відв'язка Discord; усі дії `UserManagementService` (дія — `UserAccountAction.AuditAction`); створення й відкликання API-токенів; створення, зміна й видалення середовищ, enrollment-токени, відкликання агента; створення, видалення й зміна джерела стеку, хук деплою; restart і down стеку, деплой вручну (панель, бот, CLI); start/stop/restart контейнера (декоратор `AuditedCommand` навколо `AuthorizedCommand`, тож і відмови); розшифрування SOPS для git-фільтра. Webhook, хук деплою з CI й rehydrate — у історії деплоїв, не в журналі. Читання журналу — `AuditService` (адміністратор без обмежень токена), фільтри `AuditFilter`, сторінки по 1–200 записів, від нових. Записи старші за `Audit:RetentionDays` (типово 365, 0 — зберігати завжди) видаляє `AuditRetention` при старті й раз на добу.
  - Панель: `/audit` («Адміністрування» → «Журнал аудиту»), модель — `src/features/audit/model.ts`: фільтри в search params (`category`, `outcome`, `user`, `environment`, `q`, `from`/`to` — локальні дні, `to` включно; `page`), пошук іде до ЦА лише на Enter, сторінка — `keepPreviousData`.
