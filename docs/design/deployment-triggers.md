# Webhook і хук деплою

Шляхи `Domain/…`, `Application/…`, `Infrastructure/…`, `Api/…` — відносно `src/Aggregator`, шляхи панелі (`src/features/…`, `src/components/…`) — відносно `src/Web`.

## Webhook-деплой

- **Webhook-деплой.** Секрет — на репозиторії (`GitRepository.ProtectedWebhookSecret`, `ISecretProtector` з `SecretPurpose.WebhookSecret`): його створює й видаляє той, хто може змінювати репозиторій (`POST|DELETE /api/repositories/{id}/webhook`), показується один раз, у відповіді на створення; новий замінює старий. Webhook організації — секрет на підключенні (`GitConnection.ProtectedWebhookSecret`, лише адміністратор, `/api/git-connections/{id}/webhook`), прийом — `POST /api/webhooks/connections/{connectionId}` (`PushWebhookService.ReceiveForConnectionAsync`): після перевірки підпису репозиторій шукається серед репозиторіїв підключення за адресою з тіла (`repository.clone_url`/`html_url` у GitHub і Gitea, `project.git_http_url`/`web_url` у GitLab; `PushEvent.RepositoryUrls`) через `GitUrl.Key`; не знайдено — `Ignored`. Стек середовища, якому підключення більше не дозволене, — `NotAllowed`. Стек вмикає деплой після push сам (`Stack.DeployOnPush`, типово вимкнено, `PUT /api/stacks/{id}/deploy-on-push`, роль Editor, для системного стеку — 409): один webhook на репозиторій обслуговує всі стеки, а вирішує той, хто відповідає за стек.
  - Прийом — `POST /api/webhooks/{repositoryId}` без автентифікації (`PushWebhookService`): автентифікує сам секрет. Тіло читається сирим (до 5 MiB, інакше 413), бо підпис покриває точні байти. Провайдери — ієрархія `GitWebhookProvider` → `HmacWebhookProvider` → `GitHubWebhook` (`X-Hub-Signature-256: sha256=<hex>`), `GiteaWebhook` (`X-Gitea-Signature`, також Forgejo), а `GitLabWebhook` порівнює `X-Gitlab-Token` з секретом. Gitea надсилає ще й заголовки GitHub, тому її провайдер питається першим. Усі порівняння — `CryptographicOperations.FixedTimeEquals` над SHA-256 обох значень (не видає й довжини). Невідомий репозиторій, репозиторій без секрету, невідомий відправник, неправильний підпис і нечитабельний секрет — однаковий 401 (`WebhookRejectedException`); тіло не JSON — 400 лише після перевірки підпису. Ні тіло, ні підпис не логуються.
  - `ping` GitHub — `Pong`, інші події, теги й видалена гілка — `Ignored`. Push у гілку деплоїть стеки цього репозиторію з тією самою гілкою й `DeployOnPush`: `Deployment.QueueFromWebhook` (тригер `Webhook`, без користувача, `pull: missing`). Деплой бере голову гілки, а не `after` з тіла: повторно надіслана стара доставка передеплоїть поточну голову, а не відкотить стек. Відповідь (`WebhookResponse`) — для журналу доставок на git-сервері: що сталося з кожним стеком.
  - Стек, що вже працює на коміті `after`, — `AlreadyDeployed` (повторна доставка); офлайн-агент — `AgentOffline`, нічого не ставиться (інваріант 7). Деплой у черзі (`Queued`) — `AlreadyQueued`: статус `Running` зберігається до fetch, тож він ще візьме цей push. Деплой, що вже йде з тим самим комітом, — `AlreadyRunning`, з іншим — `AfterRunning`: `PushDeploymentGate` (singleton) запам'ятовує стек, а `PushFollowUpObserver` (`IDeploymentObserver`) після завершення ставить новий webhook-деплой, якщо агент онлайн і ніхто не поставив свій. Рішення «запам'ятати» й «забрати» — під одним замком, а результат деплою зберігається до спостерігачів, тож push не губиться між ними. Пам'ять гейта не переживає рестарту ЦА, але й деплой, що йшов, тоді позначається Failed: push треба надіслати повторно з git-сервера (Redeliver).

## Хук деплою

- **Хук деплою** (deploy hook) — для образів із рухомим тегом: деплой за push бере лише відсутні образи, тож CI після push образу викликає хук стеку, і той деплоїться з `pull: Always`. Токен — на стеку, зберігається лише хеш (`Stack.DeployHookTokenHash`, `SecretToken.Hash`, перевірка `AcceptsDeployHook` за сталий час): ЦА не треба його читати, лише порівнювати. Створює (новий замінює старий, показується один раз) і видаляє Editor стеку (`POST|DELETE /api/stacks/{id}/deploy-hook`, `StackService`), для системного стеку — 409. Виклик — `POST /api/deploy-hooks/{stackId}` без автентифікації з `Authorization: Bearer <token>` (не в адресі: її зберігають логи проксі й CI), тіло ігнорується (`DeployHookService`): `Deployment.QueueFromDeployHook` (тригер `DeployHook`, без користувача, голова гілки), 202 з `Queued`; деплой у черзі, що й так тягне всі образи, — `AlreadyQueued`; інший незавершений деплой — `AfterRunning`: `PushDeploymentGate` пам'ятає для стеку політику pull, `Always` хука не перекривається пізнішим push, а `PushFollowUpObserver` ставить `QueueFromDeployHook` і, якщо між ними хтось поставив деплой без pull, чекає й за ним. Невідомий стек, стек без хука, немає чи неправильний токен — однаковий 401 (`WebhookRejectedException`); офлайн-агент — 503, нічого не ставиться.
