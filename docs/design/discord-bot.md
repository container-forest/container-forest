# Discord-бот: шлюз і меню

Конвенції коду бота — [src/DiscordBot/CLAUDE.md](../../src/DiscordBot/CLAUDE.md). Шляхи `Domain/…`, `Application/…`, `Infrastructure/…`, `Api/…` — відносно `src/Aggregator`, шляхи панелі (`src/features/…`, `src/components/…`) — відносно `src/Web`.

## Шлюз і токен

- **Discord-бот:** контракт — `src/Contracts/bot/bot.proto` (пакет `bot`), бот лише клієнт. Сервісний токен у metadata `x-bot-token` (у ЦА — лише хеш), Discord ID користувача — поле кожного запиту. ЦА перевіряє права прив'язаного користувача так само, як для панелі; помилки — коди статусу gRPC, для `UNAUTHENTICATED` причину уточнює трейлер `x-cf-reason` (`invalid-bot-token` / `account-not-linked`).
- Токен бота задається конфігурацією, а не видається ендпоінтом: він рівносильний адмінському доступу, тож випустити його має лише той, хто має доступ до сервера ЦА, а не будь-яка адмінська сесія в браузері. ЦА: `CF_BOTGATEWAY__TOKENHASHES__0` (`__1`, …) — SHA-256 токена, 64 hex-символи в нижньому регістрі, як `SecretToken.Hash`; перевірка — `SecretToken.Matches`; неправильний формат хешу зупиняє старт (`ValidateOnStart`). Бот: `CF_BOT__SERVICETOKEN`. Генерація: `openssl rand -hex 32`, хеш — `printf '%s' "$TOKEN" | sha256sum`. Без жодного хешу `BotGateway` відхиляє всі виклики (`invalid-bot-token`). Кілька хешів — для ротації без простою: додати новий → перезапустити ЦА → перевести бота → прибрати старий. Токени в БД — лише коли знадобиться кілька ботів або ротація з панелі; контракт від цього не зміниться.
- `BotGatewayService` (порт gRPC той самий, що для агентів): `BotGatewayInterceptor` перевіряє токен і перекладає винятки на коди статусу з `bot.proto`; кожен виклик від імені користувача кладе його `UserId` у `HttpContext.User` (claim `NameIdentifier`), тож далі працюють ті самі сервіси й перевірки прав, що й для панелі.
- `BotGatewayInterceptor` перевіряє токен для всіх видів викликів, включно з потоковими: базовий `Interceptor` пропускає їх без перевірки.

## Прив'язка акаунта

- Прив'язка Discord-акаунта — доменна сутність `DiscordLink` (таблиця `DiscordLinks`, один запис на користувача, Discord ID унікальний), а не зовнішній логін ASP.NET Identity: бот не залежить від Identity, і прив'язка працює ще до логіну. Основний спосіб — прив'язка через Discord OAuth2 у панелі (ADR-0009); альтернатива — одноразовий код з панелі (`/api/me/discord/link-code`, 8 символів без схожих літер, 10 хвилин, зберігається лише хеш) і `/link <код>` у боті (`LinkAccount`). Вхід через Discord шукає користувача за тим самим `DiscordLink`. Повторна прив'язка того самого Discord-акаунта переносить її на нового користувача.

## Меню /dashboard

- **`/dashboard`** (`src/DiscordBot/Dashboard`, модуль і рендерер — `Interactions/DashboardModule.cs`, `DashboardRenderer.cs`): одне ephemeral-повідомлення на Components V2, яке кожне натискання редагує на місці (defer → `ModifyOriginalResponseAsync` з `MessageFlags.ComponentsV2`); follow-up повідомлень бот не надсилає, усе — в одному повідомленні, стан у ньому просто оновлюється. Екрани: середовища → стеки середовища (по 5 на сторінку, «Up» — час деплою, кількість запущених контейнерів) → стек (контейнери, Redeploy, Redeploy + pull, Restart, Down) → підтвердження для redeploy і down; restart — без підтвердження, як у панелі. Бот без стану: маршрут екрана (`DashboardRoute`) записаний у `custom_id` кнопки як `dash:<вид>:…`, GUID — 22 символи base64url, щоб уміститися в 100 символів; невідомий id (зі старішої версії меню) відкриває список середовищ. Кожне натискання завантажує дані заново й виконується від імені того, хто натиснув: меню ephemeral, тож це той самий користувач. Кнопки ховаються за `can_restart`, `can_take_down`, `can_deploy` і вимикаються, поки агент офлайн або дія виконується; restart і down спершу показують екран із вимкненими кнопками, потім результат із кінцем виводу compose. Redeploy ставить деплой у чергу (`DeployStack`), а бот сам стежить за ним (`GetDeployment` кожні 3 с) і редагує повідомлення, коли змінюється стан, з вимкненими кнопками, доки деплой не завершиться; після 13 хв (Discord дає редагувати повідомлення 15 хв після натискання) показує «ще йде» і «Refresh», який стежить знову. Логіка (`DashboardService`) не залежить від Discord.Net і тестується із заглушкою `IForestClient`; що шаблон `[ComponentInteraction("dash:*")]` ловить кожен маршрут, перевіряє тест через `InteractionService.SearchComponentCommand`. Ліміти Discord: до 40 компонентів і 4000 символів тексту на повідомлення, до 5 кнопок у рядку.
