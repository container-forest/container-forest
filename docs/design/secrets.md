# Секрети: SOPS, git-фільтр, rehydrate

Рішення — [ADR-0003](../adr/0003-secrets-at-rest.md), [ADR-0010](../adr/0010-git-secrets-filter.md). Як агент пише секрети — [src/Agent/CLAUDE.md](../../src/Agent/CLAUDE.md). Шляхи `Domain/…`, `Application/…`, `Infrastructure/…`, `Api/…` — відносно `src/Aggregator`, шляхи панелі (`src/features/…`, `src/components/…`) — відносно `src/Web`.

## Ключі й розшифрування в ЦА

- **SOPS.** Ключі — доменна сутність `AgeKey` (таблиця `AgeKeys`): age-пара X25519 на середовище, приватна частина зашифрована `ISecretProtector` з `SecretPurpose.AgeIdentity`, у відповідях — лише `recipient`. Ключів на середовище може бути кілька (ротація): новий шифрує нові файли, усі разом розшифровують. Створює й видаляє адміністратор або адміністратор середовища (`AgeKeyService`; ключ може належати стеку, ADR-0012), публічні ключі бачить кожен, хто бачить середовище (вони потрібні для `.sops.yaml`). Пару генерує `age-keygen` (`AgeKeygenCli`), вивід розбирається й ніде не логується.
- `SopsDecryptStep` (одразу після `GitFetchStep`): файл вважається зашифрованим, лише якщо має метадані sops свого формату (`SopsFile.IsEncrypted`: ключ `sops:` верхнього рівня в YAML, об'єкт `sops` у JSON, `sops_version=` у dotenv, `[sops]` в INI, `{"data", "sops"}` для решти, тобто двійкових), бо файл, що лише згадує sops чи `ENC[`, має деплоїтися як є. Формат — за розширенням, як у самого sops. Розшифровуються вони лише ключами цільового середовища; без ключа, з чужим ключем або з нечитабельним приватним ключем — помилка деплою з підказкою. Розшифрований файл іде агенту з `StackFile.secret = true` (tmpfs + символьне посилання), у лозі деплою — лише шляхи.
- `SopsCli` запускає `sops decrypt --filename-override <шлях> /dev/stdin`: шифротекст — через stdin, відкритий текст — через stdout, на диск ЦА нічого не пишеться. Ключі — у `SOPS_AGE_KEY` (через `\n`) дочірнього процесу; `CliProcess` очищає його оточення (лишається `PATH`), тож `CF_*` ЦА до sops не потрапляють. Код виходу 128 (`CouldNotRetrieveKey`) — «жоден ключ середовища не є отримувачем», решта — перший рядок stderr (sops не друкує відкритого тексту).
- `sops` і `age-keygen` — бінарники в образі ЦА: їх ставить `scripts/install-sops.sh` (версії й SHA-256 для amd64/arm64 — у скрипті, оновлювати там) в окремій стадії Dockerfile. Шляхи й тайм-аут — `Sops:SopsPath`, `Sops:AgeKeygenPath`, `Sops:Timeout`. Тести зі справжніми інструментами (`SopsToolsTests`) без них пропускаються, а в CI (`CF_TEST_REQUIRE_SOPS=1`, інструменти ставить той самий скрипт) падають.

## SOPS для git-фільтра в ЦА

- **SOPS для git-фільтра** (ADR-0010, `SopsSecretsService`, `Api/Contracts/SopsContracts.cs`).
  - `POST /api/sops/decrypt`: потрібен `AccessScope.CanDecryptSecrets` (сесія — так; токен — лише з прапорцем `secrets`, claim `cf:secrets`, ніколи разом із лише читанням). Ключі — ті, чиї `recipient` є в метаданих файла (`SopsFile.AgeRecipients`, лише підказка) і чиє середовище в `AccessPolicy.EditorEnvironments` актора; адміністратор без обмежень — усі. Жодного ключа ЦА серед отримувачів — `SopsDecryptionException` (422), лише чужі середовища — 403. Лог — хто й який шлях, без вмісту.
  - `POST /api/sops/encrypt`: будь-який актор, крім лише читання. `YamlSopsConfigReader` обирає перше правило `.sops.yaml` за `path_regex` (шлях від кореня репозиторію, `RegexOptions.NonBacktracking` замість RE2) і приймає лише `age` та параметри «що шифрувати»; інший тип ключа — `SopsConfigException` (400). `SopsCli.EncryptAsync` пише тимчасовий JSON-конфіг лише з цим правилом і запускає `sops --config <файл> encrypt`: `.sops.yaml` репозиторію до sops не потрапляє, тож KMS, Vault і PGP ЦА не викликає. Помилка sops — 422, у лог лише код виходу (stderr може цитувати відкритий текст).
  - Обидва — до 1 MiB вмісту, ліміт `sops` на користувача (token bucket: 300, +60 за 10 с).
  - `SopsDecryptStep` спершу перевіряє `.gitattributes` (`GitAttributes`, правила `.gitignore` лише для атрибута `filter`): файл під `filter=forest` без метаданих sops — помилка деплою. Файли `.gitattributes` каталогів вище стеку `LibGit2SharpGitSource` кладе в `GitSnapshot.OuterAttributes`.

## Git-фільтр у CLI

- **Git-фільтр** (`src/Cli/Secrets`, ADR-0010). `forest git setup` пише в локальний конфіг клону `filter.forest.process` (`forest git filter-process`, абсолютний шлях бінарника в одинарних лапках, якщо це сам `forest`), `filter.forest.required`, `diff.forest.textconv`, `forest.context` і ставить pre-commit хук (`forest secrets check --staged`; чужий хук не перезаписує), потім заново checkout'ить зашифровані незмінені файли під фільтром.
  - `GitFilterProcess` — протокол pkt-line версії 2 (`PktLineReader`/`PktLineWriter`), можливості clean і smudge; кожен файл — `SmudgeOperation` або `CleanOperation` (Template Method над `FilterOperation`), бекенди — `ISopsBackend` (`AggregatorSops` через `ForestApi`, `LocalSops` з `forest.localSops`).
  - Smudge без доступу повертає шифротекст і success (причина в stderr один раз); clean при будь-якій помилці — `status=error`.
  - `FilterCache` (`.git/forest/cache.json`, ключ HMAC `.git/forest/key`, 0600) повертає незміненому тексту той самий шифротекст; `secrets updatekeys` забуває записи й робить `git add --renormalize`.
  - `secrets remove` знімає фільтр із файла: свій рядок `.gitattributes` видаляє, для шаблону дописує `/<шлях> -filter -diff` (якщо глибший `.gitattributes` усе одно вмикає фільтр — відкат і відмова); типово в клоні повертається шифротекст із git (незакомічені зміни — відмова), `--plain --yes` індексує відкритий текст. `secrets rule list|add|remove` редагує `.sops.yaml` через `SopsConfigFile`: рядки блокового списку `creation_rules`, коментар перед правилом належить йому, незмінені правила пишуться як були, чужа форма (flow-стиль, блокові скаляри, списки ключів) — відмова; нове правило — перед першим, з яким перекривається, з ключами, спільними для всіх правил і не чиїми-небудь ключами середовищ (резервні). `git teardown` (`GitFilterSetup.Remove`) — протилежність `setup`: секції `filter.forest`, `diff.forest`, ключі `forest.*`, свій хук, `.git/forest`, шифротекст у робочих файлах; незакомічені зміни — відмова.
  - Закінчення рядків: git перетворює їх до smudge, тож рядки `.gitattributes` пишуться як `filter=forest diff=forest eol=lf` (`SecretsFiles.FilterAttributes`; старі без `eol` — `LegacyFilterAttributes`, `AddAttributes` дописує їм `eol=lf`). `secrets fix-eol` робить те саме для кореневого `.gitattributes`, кладе в індекс шифротекст без CR через `hash-object` + `update-index` (не `git add`: той узяв би й незакомічені зміни відкритого тексту) і перечитує файли. `GitFilterSetup.Refresh` перечитує й шифротекст, що відрізняється від git лише CR, і повертає stderr checkout'а (причина від фільтра); `setup`, `status`, `check` попереджають про правила без `eol=lf`, `check` відхиляє шифротекст із CRLF. Clean знімає CR з dotenv та INI (`SopsFiles.PlainForSops`) до кешу й шифрування. ЦА шифротекст не нормалізує, лише називає CRLF у помилці (`SopsCli`).

## Rehydrate

- **Rehydrate.** Файлові секрети живуть у tmpfs і зникають із перезавантаженням хоста. `DockerEnvironment.RecordConnection` порівнює `boot_id` з `Hello` з попереднім; новий — і `AgentGatewayService` після `registry.Open` (деплої йдуть цьому агенту) викликає `SecretRehydrationService`. Той ставить у чергу `Deployment.QueueRehydrate` для кожного стеку з `Stack.NeedsRehydration`: є `DeployedCommit`, останній успішний деплой мав секретні файли (`DeployedWithSecrets`, з `DeployContext.HasSecretFiles`), не системний. Стек із незавершеним деплоєм пропускається: той сам надішле секрети. Помилка постановки лише логується, з'єднання не страждає. Перший `Hello` після реєстрації (`LastBootId` = null) і перепідключення без перезавантаження нічого не деплоять.
- Деплой rehydrate закріплений на коміті з моменту постановки (`IsPinned`, тригер `Rehydrate`, без користувача, `pull: missing`): гілка могла піти вперед, а відновлення секретів не має деплоїти нічого нового. `GitFetchStep` для нього все одно робить fetch гілки (кеш міг зникнути), але читає закріплений коміт; недоступний git-сервер — лише попередження, коміт береться з кешу ЦА. Результат іде в історію деплоїв і сповіщення, як звичайний деплой. Застереження: джерело стеку (`ChangeSource`) після останнього деплою не відстежується, і rehydrate читає закріплений коміт за поточним джерелом.
- Після перезавантаження хоста Docker піднімає контейнери раніше, ніж агент підключається, тому контейнери з файловими секретами падають до rehydrate. Новий `boot_id` у `Hello` — сигнал для ЦА повторно надіслати секрети.
